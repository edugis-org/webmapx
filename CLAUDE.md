# webmapx

Modular web map UI with adapters for MapLibre, OpenLayers, Leaflet, and Cesium.

## Stack

- **Framework**: Lit (web components), TypeScript, Vite
- **Map engines**: MapLibre GL, OpenLayers (ol), Leaflet, Cesium
- **Overlays**: @allmaps (leaflet, maplibre, openlayers)
- **UI**: Shoelace components
- **State**: `src/store/map-state-store.ts`

## Architecture

```
src/
  map/                    # Engine adapters + services
    IMapInterfaces.ts     # Shared interfaces
    base-adapter.ts       # Abstract base: store, hasLayer, layer bookkeeping
    maplibre-adapter.ts   # MapLibre adapter (extends BaseAdapter)
    openlayers-adapter.ts
    leaflet-adapter.ts
    cesium-adapter.ts
    maplibre-services/    # Engine-specific services (pure engine, no store bookkeeping)
    openlayers-services/
    leaflet-services/
    cesium-services/
    layer-source-utils.ts
    logical-layer-executor.ts
    runtime-layer-utils.ts
    adapter-registry.ts
  components/             # Lit web components (webmapx-*)
  store/                  # Map state (IMapState.ts, map-state-store.ts, map-events.ts)
  config/                 # Config types
  tools/                  # Map tools
  utils/                  # Shared utilities
  workers/                # Web workers
```

## Key patterns

- **Stories tool** (`webmapx-stories-tool.ts`, config `stories` section, `src/config/types.ts`): a guided-tour tool — `StoryConfig` → `StoryChapterConfig` → `StoryStepConfig`. Each step's `state` is authored as human-readable `StoryStepConfigState` (`layers`, `hiddenLayers`, `view: { center, zoom, bearing?, pitch? }`, `transparency`, `projection`, `terrain`) and converted via `toStoryStepState` (`src/config/story-step-state.ts`) into the short-key `StoryStepState` — the same shape as a decoded permalink (`PermalinkState` in `src/utils/permalink.ts`) — camera + layer visibility/opacity + terrain, with no tool state — so applying a step is a set of direct `adapter.setViewport`/`setBearing`/`setPitch`/`setLayerVisibility`/`setLayerOpacity`/`setProjection`/`setTerrainEnabled` calls. Layer visibility/transparency are additionally mirrored into `store.mapLayers` (same dual update `webmapx-layer-overview.ts` does for its own toggle/slider handlers) so the legend reflects what a story step is showing; camera/projection/terrain are not dispatched, since `captureStartState`/`restoreStartState` already give the story its own restore path for those and no UI needs them live. `captureStartState`/`restoreStartState` snapshot and restore camera + layer visibility/opacity (both engine and store) + projection + terrain around the whole story, so it's still a transient overlay — the map ends up exactly as it was before the story opened, and nothing leaks into the permalink (which is generated from `store` state after the story has closed). Unlike permalink restore (which only toggles layers already loaded and reports the rest as missing), a story step lazily adds any referenced layer that isn't loaded yet via `mapHost.addLayerRequest({ layerId })` — the same catalog-lookup path `webmapx-search-tool.ts`/`webmapx-buffer-tool.ts` use — tracked in `addedLayerIds`. A story-added layer no longer referenced by the current step is removed outright (not just hidden) as soon as you navigate away from it, and any layer still in `addedLayerIds` when the story closes is removed then too — so which layers the legend lists depends only on the current step, never on which steps happened to be visited earlier. A layer that was already on the map before the story opened is never removed by the story (only hidden/restored), since the story doesn't own it. Step content is `html` (inline, sanitized) or `htmlUrl` (fetched, resolved relative to the config file's URL at load time in `config/loader.ts`; relative `src`/`href` inside the fetched HTML are then resolved against that URL too, via `sanitizeAbstractHtml(html, baseUrl)` in `utils/sanitize-html.ts`).
- **Geoprocessing tool** (`webmapx-geoprocessing-tool.ts`, tool type `geoprocessing`, label "Analysis"): one panel for every vector overlay/selection operation, because they are all the same pipeline (1–2 layers → a few params → one `ogr2ogr` call → new layer) differing only in an SQL template. Operations are **data**, not components: `src/utils/geoprocessing-operations.ts` holds `GEO_OPERATIONS` (clip, erase, intersect, union-overlay, select-by-location, spatial join, dissolve, centroid, convex hull, simplify, buffer, voronoi, delaunay, cartogram), each declaring `inputs` (arity + role labels), `params` (`number`/`select`/`field`), and `buildSql(ctx)`. Adding an operation is a registry entry plus a diagram — no UI work. The UI is progressive disclosure on one panel (operation grid collapses to a chip, inputs appear below), never a wizard with a back button, which would drop parameter state.
  - **Inputs are materialised into one indexed SpatiaLite database before the SQL runs** (`buildWorkingDatabase`), and that is the difference between a usable tool and a frozen minute. Running SQL straight against the reprojected GeoJSON makes OGR's SQLite dialect re-parse geometry out of JSON on every access: 144×576 polygons of 401 vertices took **19.8 s**, and **1.3 s** once the same data sat in native SpatiaLite storage — the algorithm was never the bottleneck. `SPATIALITE=YES` also builds an R-tree per table, which `indexedPairs` uses for pairwise joins (1.33 s → 0.75 s). Both inputs must share **one** database (cross-database SQL only works while the outer dataset is GeoJSON/VirtualOGR, and gdal3.js cannot append to an existing DB), so an **OGR VRT** presents the two files as one multi-layer source. Measured end to end at 256×1600: union 15.0 s → 2.2 s, intersect 13.0 s → 0.6 s.
    - **Shrinking the subtrahend is a trap; measure before believing it.** `differenceFromAll` deliberately subtracts the *whole* dissolved other layer. On 4000 regions against 257 real countries (120k vertices): global union **30 s**, per-row union of R-tree neighbours **96 s**, aggregate `ST_Union` over a join **96 s**. A correlated subquery re-runs per row and that dwarfs the cost of the bigger geometry. A cheap index `EXISTS` that skips rows with no neighbour (keeping the global union) saves 8% — not worth the SQL. An `MbrIntersects` prefilter in a WHERE clause buys 6% for the same reason: it still visits every pair.
    - **Union is inherently the expensive one** — measured end to end on 257 real countries × 4000 regions: clip 4.1 s, intersect 5.4 s, union 38.4 s. Its two difference branches each dissolve the opposite layer and then subtract per feature, which is most of the time. That is why cancel and elapsed-time feedback exist rather than a progress bar: GDAL offers no progress for a single synchronous SQL call.
  - **Two different waits, two different fixes.** Choosing an operation felt unresponsive because collecting attribute names walks every feature of the source on the main thread — it now waits for `afterPaint()` so the form appears first. Pressing Calculate felt slow because GDAL WASM was loaded on first use; `prewarmSpatialWorker()` is called (deferred past paint) when the panel opens, so the load overlaps with reading and filling in the form. `prewarmSpatialWorker` existed but had no callers.
  - **A calculation can be cancelled, and cancelling means terminating the worker** (`cancelSpatialOps`). GDAL runs one synchronous WASM call that ignores further messages, so there is nothing to politely ask; the next operation recreates the worker and reloads GDAL (~3 s). It is therefore an explicit user action only, never automatic — the worker is shared, so it aborts unrelated spatial work such as a file import. `SpatialOperationCancelled` exists so the tool reports a cancellation as a notice rather than a red error.
  - **Attribute aggregation is a param kind, not an operation.** `kind: 'aggregations'` is a repeatable field+function list (`sum`/`mean`/`min`/`max`/`count`) that becomes `SUM(a."pop") AS "pop_total"` in the existing `GROUP BY` — the PostGIS aggregates without typing SQL. `dissolve` uses it (provinces → country with populations added up, the common case) and so does `statistics`, which is the same grouping *without* `ST_Union`: no geometry, no expensive geometry work, result rendered as a table in the panel. Deliberately **not** built: dissolve into connected components (islands per country). It needs a multi-step runner and answers a question students rarely ask; dissolve-by-attribute covers "provinces → country" and "buildings → blocks per street".
    - **Summing a text column is not an error in SQLite, it silently returns nonsense** (summing ISO country codes produced `-396`). The guard belongs on the *function* list, not the field list: every field is always offered, and `total`/`average` disappear for a field not observed to hold numbers (a field that is numeric in some features and text in others counts as text). Filtering the fields by the chosen function instead — the first attempt — inverted the natural order and made text fields look unavailable.
    - **`list` is PostgreSQL's `string_agg`, rebuilt.** SQLite 3.45 rejects `ORDER BY` inside `group_concat` *and* refuses `group_concat(DISTINCT x, separator)` — both verified against the bundled build, not assumed. A correlated subquery per group does all three (separator, uniqueness, sort order) at once; correlating per *group* is cheap, unlike the per-row correlation that made union crawl.
    - `outputGeometry: 'table'` short-circuits the runner's reprojection *and* `dropEmptyGeometries` — rows without geometry would otherwise all be discarded — and makes the tool render a table instead of calling `addLayerRequest`, hiding the output-layer-name field with it.
    - **Edit handlers for repeatable rows must read the current value, not the rendered copy.** Changing a row's field and then its function within one render otherwise starts both edits from the same stale array, and the second silently undoes the first. The browser test caught this as a column named `name_total`.
  - **`simplify` must not use `ST_Simplify`.** Both GDAL variants simplify one geometry at a time, so a border shared by two municipalities is simplified twice, independently, and the halves no longer match — slivers and overlaps along every shared edge ("PreserveTopology" only promises each polygon stays valid *on its own*). `simplifyShared` builds a topology first (`topojson-server`), so coincident boundaries become one arc simplified once (`topojson-simplify`, Visvalingam) and both neighbours keep identical points. This is what mapshaper does; mapshaper itself is 15 MB unpacked and drags in GeoPackage and zstd-wasm, the topojson modules are ~60 KB. Fast enough to be a non-issue: 257 countries / 294k coordinates in ~90 ms. The old fast-vs-topology-preserving choice is gone — the fast option was simply the broken one.
    - **Topology sharing is not the whole story — simplification also creates self-intersections**, which render as stray triangles (first seen on the Morocco/Mauritania and Chad/Nigeria borders at a 100 km tolerance). mapshaper repairs these by default; `topojson-simplify` does not. `simplifyShared` therefore keeps a **threshold per arc** instead of one for the whole topology, detects rings that cross themselves, and quarters the threshold (halving the linear tolerance) on just the guilty arcs, up to `MAX_REPAIR_PASSES`; the last pass restores those arcs completely rather than shipping a known crossing. Because both neighbours share the arc, repair cannot break border matching. Cost on 257 countries: 70–260 ms, still keeping only ~7% of points.
    - Tolerance is an **area** threshold (`t²`), matching mapshaper's `interval=`: a narrow bend of that size disappears, a wide shallow curve of the same depth survives. Don't describe it as a deviation.
    - **Arc sharing needs *exactly* equal coordinates.** `topology()` matches points exactly, with no snapping (mapshaper has `snap`). Data whose shared borders differ even by a millimetre — separately exported layers, tile-clipped geometry — will be simplified independently and produce real slivers. Inputs that come from one source (the demo's `world-countries` TopoJSON) are fine; if this ever bites, snap before building the topology rather than quantizing, which would move every coordinate.
    - The regression test asserts that both neighbours emit the **exact same** points along a shared border. It must deduplicate ring points first — a ring repeats its first point at the end, and the two neighbours start their rings in different places.
  - **An operation is computed by SQL *or* by JS, never both**: `buildSql` for anything SpatiaLite can express, `compute` (a `GeoCompute`, receiving the input already in EPSG:3857) for what it cannot — `labelPoint`, which uses mapbox's `polylabel` for the pole of inaccessibility because `ST_PointOnSurface` guarantees only *a* point inside, usually hard against an edge; `simplify`; and `voronoi`/`delaunay`. The last two are JS despite SpatiaLite having `VoronojDiagram`/`DelaunayTriangulation`, because those return the whole diagram as **one** collection and splitting it back into one row per input point — the only way a cell can keep its point's attributes — needs the `ElementaryGeometries` virtual table, which gdal3.js does not expose; `d3-delaunay` indexes cells *by input point*, so the attribute join is free. Non-point input takes part through the average of its coordinates rather than being dropped, and collinear input is rejected explicitly: d3 jitters it and returns a zero-area triangle instead of failing.
    - **A planar triangulation has to be unwrapped across the antimeridian** (`unwrapAcrossDateline`): +20 037 508 and -20 037 508 are the same meridian, but d3 sees two clusters half a planet apart, so cells run across the Pacific and triangles link the wrong neighbours. Every negative-x site is shifted one world east when that makes the group *narrower* — a worldwide layer is left alone because shifting does not narrow it — and the resulting >180° longitudes are normalised by the `-wrapdateline` already on the runner's way back to WGS84. Per-feature centres need the same treatment (`averagePosition`): a polygon the runner's `-clipsrc` cut at the line has half its coordinates at each edge, and a naive mean puts Fiji's "centre" off the coast of Africa. Geometry alone cannot test this — `-wrapdateline` makes even a wrong-way triangle come back looking local — so the delaunay test counts *which points are neighbours* (4 of 5 triangles cross the line in the right frame, 3 in the wrong one).
    - **Unwrapping only helps a layer that fits in one world; a worldwide one needs three** (`worldCopies`, `REPLICA_OFFSETS`). World country centroids span the globe, so there is no empty side to rotate the seam into: the plane keeps a seam down the Pacific, the two countries either side of the line are not neighbours, and their cells run out to the edge of the diagram. Every point is therefore copied one world east and west, the copies shaping the cells without producing features of their own. It is gated on the layer actually spanning more than half the world, because copying a *local* layer changes its result: three nearly collinear points have a circumcircle thousands of kilometres wide, big enough for a copy one world away to fall inside it and suppress the triangle. On three worlds each triangle exists three times, so delaunay keeps the one whose centre falls in the middle world and drops anything wider than half the world (a point joined to a distant copy, not across the line).
    - **The wrap back has to be done here, not by `-wrapdateline`** (`splitAtDateline`). Reprojection folds a coordinate past ±180° back into range *without* splitting the ring first, so a cell hugging the date line returns as a polygon stretched 355° the wrong way — measured: ten of 257 cells, which is precisely the "overlapping cells and lines across the whole globe" symptom. Voronoi cells and triangles are convex, so Sutherland–Hodgman against the two meridians is exact; the ring is clipped shifted one world either way to collect the pieces belonging on the far side. End to end on the 257 centroids: 0 parts outside ±180, and 4000 sample points each land in exactly one cell.
    - A test fixture for this must be **asymmetric and gap-free**: the clip box is centred on the points, so its edge lands exactly on the wrap-gap midpoint — which for evenly spaced points *is* the correct bisector, making a broken diagram agree with a correct one. The fixture therefore puts the two points flanking the line at opposite latitudes (slanted bisector vs straight box edge) and spreads points right round the globe so unwrapping cannot rotate the seam away. Both branches share the same 3857 round trip, metric scaling and empty-geometry filter, so JS is not a second pipeline. A unit test enforces the exactly-one invariant; `Record<GeoOperationId, TemplateResult>` in the diagrams module makes a missing diagram a compile error.
  - **The JS branch needs `-s_srs EPSG:3857` on the way back.** It writes its result as plain GeoJSON, which GDAL reads as WGS84 by default, so without it every feature lands near 0,0 — indistinguishable from correct output if your test fixtures happen to sit at the map's default centre. That is why `tool-geoprocessing.mjs` builds its fixtures at `ORIGIN = [30, 40]`.
  - **GDAL writes a legacy `crs` member into everything it produces, and it has to be stripped** — at *every* point where GDAL output enters the app, which is why `utils/geojson-crs.ts` exists rather than a habit each caller has to remember: the geoprocessing runner and the file-import worker (`filePathToFeatureCollection`, which is how a dropped GeoPackage or shapefile arrives) both go through it. RFC 7946 removed the member; GDAL still emits `urn:ogc:def:crs:OGC:1.3:CRS84`, which only restates what the spec guarantees. OpenLayers honours it as the *data* projection when the layer is added and then cannot build a transform from that spelling into a proj4-registered view projection, so adding any result to a map in an equal-area projection died with `transformFn is not a function` — thrown from OL geometry code, a whole subsystem away from the tool that showed the message, and only ever on a non-Mercator view.
  - **The pipeline lives in `src/workers/geoprocessing-runner.ts`, and takes the GDAL instance as an argument** rather than importing it, so it is free of Vite `?url` asset imports and `tests/geoprocessing.test.ts` can run the *real* SpatiaLite WASM under Node against every SQL template. That test is the only thing that proves the SQL is valid; string assertions would not. `spatial.worker.ts` just routes the `geoprocess` op to it.
  - **Everything runs in EPSG:3857, not lon/lat**: SpatiaLite predicates are planar, so a tolerance in degrees means different things at different latitudes. Inputs are reprojected in, the result reprojected back, and metric params (`METRIC_PARAMS`) are divided by `cos(lat)` — the same correction `buffer()` applies.
  - **`SELECT a.*` is never used.** It emits a second geometry column and GDAL then writes the wrong one, so the runner passes explicit attribute names (read from the input GeoJSON) into `buildSql`, and colliding names from input B get a `_2` suffix. Nested/array properties are dropped: they survive GeoJSON but not a SQL column.
  - **Inputs are whatever the map has drawn, and the panel says so.** `queryLayerFeatures` hands over the full dataset for a `geojson` source but answers from `queryRenderedFeatures` for every other source type, so a tile-backed layer contributes only the current view. This is kept deliberately (it is what makes layer filters and visibility apply), but it silently changes *answers* — a union against a half-loaded layer reports the missing half as "only in the first layer" — so `isViewportLimited()` (via `adapter.getSourceConfig(sourceId).type`) shows a warning under those inputs only, an empty input explains visibility/zoom-range/filter rather than just "zoom in", and every run reports the feature counts it consumed. Never warn on all layers: a warning on every input is one students learn to ignore.
  - **`union` combines both layers' attributes.** Its three branches (overlap, A-only, B-only) are a `UNION ALL`, which matches columns *by position*, so every branch emits the identical list — A's fields, B's fields (suffixed `_2` on collision), `part` — filling `NULL` where a piece has no value. Getting the lists out of step would file B's values under A's headings rather than error.
  - **`clip` vs `intersect` differ in feature count, not geometry.** Clip (like erase) `ST_Union`s layer B into one shape first, so one input feature stays one output feature with only A's attributes; intersect deliberately runs per overlapping pair, so an input feature splits into one output feature per B feature it meets, each carrying that B feature's attributes. Getting this wrong is invisible until B has more than one overlapping feature — hence the multi-part-B regression tests for both.
  - **Two-input operations address the second layer by virtual-FS path** — `'/output/gp_b_3857.geojson'.gp_b`. Both inputs are written by the same reprojection step, so they are guaranteed to be mounted in one filesystem; this is what makes cross-layer SQL possible at all.
  - **gdal3.js build limits** (probed, not assumed): SpatiaLite 5.1.0 is present; `ST_VoronoiPolygons`/`ST_DelaunayTriangles` are **not** — the SpatiaLite spellings `VoronojDiagram`/`DelaunayTriangulation` are. Only `ogr2ogr`, `gdal_translate`, `gdal_rasterize`, `gdalwarp`, `gdaltransform`, `gdal_location_info`, `gdalinfo`, `ogrinfo` are exposed; there is no `gdal_contour`, `gdal_polygonize`, `gdaldem` or `gdalbuildvrt`, so contour/hillshade/polygonize tools are out without a recompile.
  - **Cartograms are a pure GeoJSON→GeoJSON function** (`src/utils/cartogram.ts`), wired in as the `cartogram` operation’s `compute`. **GeoJSON is lon/lat by definition (RFC 7946), so nothing here measures area in the input’s own coordinates** — a square degree is not an area, it shrinks by cos(latitude), and measuring in degrees would hand Norway twice the area it has and size the cartogram by that error as much as by the data. Areas are measured on the sphere (spherical excess, square metres) and every shape is resized in a Lambert azimuthal equal-area plane **centred on that shape**, so the factor applied is a factor of real ground area and the outline is barely deformed. Value → area goes through one shared factor (total area ÷ total value), so the layer keeps its overall size and only the *distribution* changes.
    - **The operation undoes the pipeline’s Mercator round trip itself.** The runner hands every `compute` EPSG:3857 and wants it back, but Mercator inflates area by 1/cos²(lat) — sizing Greenland from a Mercator area starts four times too big — so `fromWebMercator`/`toWebMercator` (closed-form, exact) bracket the call and keep the change local to this operation instead of teaching the pipeline about projections.
    - **Three bugs that only real data showed**, all found by sizing 265 world countries to equal area and measuring the result rather than looking at it: scaling a multipart feature about *one* centroid multiplies the distance between its parts as well as their size (Tuvalu’s nine islets, scale factor 136, ended up spread over 45 million km² — larger than Russia), so each part is now grown about its own centre with one shared factor; a longitude step read the long way round the globe inverts the area of any ring crossing the date line (`shortestLongitudeStep`), and the same wrap put a straddling country’s centroid in the wrong ocean (`datelineShift`); and a ring that encircles a pole defeats the spherical-excess formula entirely, which is measured in an equal-area plane instead. Dorling circles are also kept off the poles, since a crowded layout otherwise pushes them over the top.
    - **One factor is not enough, so the achieved area is measured and corrected** (`AREA_TOLERANCE`, up to four passes). A ring’s edges are straight in lon/lat and scaling bends them, so the result drifts from factor² — 0.0001% for a half-degree shape, 3.5% for a city state blown up to the size of a country. Measured on 265 countries: sizing by each country’s own area reproduces the input to **0.003%**, sizing by a constant equalises every country to a ratio of **1.0002**, and area per value holds to **1.0002** (scaled) / **1.0004** (dorling) across values spanning two orders of magnitude. ~200 ms for the layer.
    - **The default is the contiguous method** (`contiguous`, Dougenik–Chrisman–Niemeyer 1985): one rubber sheet, where every boundary point moves under the summed forces of *all* regions, so neighbours stay joined and the result still reads as a map. Borders hold because the displacement is a function of position alone — two countries sharing a border share those coordinates, so both copies move identically; verified on real data (France/Germany 121 shared vertices in, 121 out; South Africa/Lesotho 291/291). Same exact-coordinates caveat as topology-aware simplification. `scaled` and `dorling` remain because they keep every outline exactly, but they leave gaps, which is what made the first version look wrong.
      - **The shared plane must be equal-area *and* shape-honest**, because the forces are isotropic: a plane that squashes one direction turns an even push into a lopsided one. Cylindrical equal-area fails badly — it compresses latitude towards the poles, so a modest force becomes a huge latitude change, and rubber-sheeting the world left Lesotho on the South Pole and dragged France into the tropics. `sharedPlaneFor` picks azimuthal equal-area for a layer under 40° across and Equal Earth (with a Newton inverse) for anything global.
      - **Flat `Float64Array`s, not arrays of `[x, y]`.** This is all points against all regions — 30 000 points and 265 countries is eight million force evaluations per pass — and pointer-chasing dominated: 31 s → under 6 s for 12 passes, with `Math.hypot` replaced by a plain `sqrt` (it guards against overflow and costs several times more).
      - **A rubber sheet trades exactness for staying joined**: measured on 265 countries with values spanning two orders of magnitude, 12 passes give a median area error of 3% but a tail — about a third of regions are still off by more than 10%, the worst being tiny regions asked to grow thousands of times. More passes help to a point (20 passes: 1.9% median) and then oscillate, which is what the `1/(1+meanError)` damping is for. Tests assert *convergence and contiguity*, not exact areas, because exact areas are not what this method promises. Gastner–Newman diffusion (Worldmapper) is smoother and needs a WASM library (`go-cart-wasm`); this is a hundred lines and no dependency.
  - **A pinned operation is how an operation gets its own toolbar entry.** `webmapx-geoprocessing-tool` takes an `operation` attribute (`pinnedOperation`); when set it selects that operation on activate, hides the operation grid and drops the “Change” button. `webmapx-cartogram-tool` (tool type `cartogram`) is a three-line subclass that pins `cartogram` — a cartogram is asked for by name, and hunting for it in a grid of fourteen operations is the wrong first experience. A subclass rather than a second component because layer picking, the numeric-attribute list, the shared GDAL worker, elapsed-time feedback, cancel, the viewport-limited warnings and `addLayerRequest` are already built here; a parallel implementation would drift within a release. `testpages/cartogram.html` drives it by hand — note the tool must sit **inside** `<webmapx-map>`, since `mapHost` resolves via `closest('webmapx-map')` and a tool outside it reports success while adding no layer.
  - **Raster analysis is deliberately absent.** Raster layers here are styled tiles (WMS/WMTS/XYZ) — analysing them is analysing a screenshot, and it yields plausible but wrong numbers, which in a teaching product is worse than no feature. Real raster tools need a GeoTIFF/COG layer type first.
- **View projections (OpenLayers only)** (`webmapx-projection-tool`, tool type `projection`, catalog in `src/utils/view-projections.ts`, engine side in `map/openlayers-services/projection-support.ts`): switches the projection the 2D map is *computed* in — distinct from `webmapx-view-mode-tool`, which switches MapLibre between Mercator and its globe (two renderings of one projection family). The point is area: Web Mercator inflates it by 1/cos²(lat), so every world-scale thematic map drawn in it overstates high latitudes, and a cartogram in Mercator is a lie by construction. Catalog carries `equalArea` (shown in the UI, and asserted in `tests/view-projections.test.ts` by measuring a projected quad rather than trusting the flag) and ships Equal Earth, Mollweide, EPSG:6933, polar LAEA/stereographic alongside Mercator and EPSG:4326.
  - **A View's projection is fixed at construction**, so `MapCoreService.setProjection` builds a new `View` and four things have to travel with it, each silent if missed: existing `VectorSource` geometry and overlay positions (already converted to the *old* projection — tiles are exempt, OL reprojects those itself and doing it here would double the shift), the resolution, the `maxBounds` extent (kept in lon/lat for exactly this reason), and the view listeners, which live on the View object rather than on the map (hence `attachViewEvents`).
  - **`resolutionScaleAt` is projection units per ground metre**: divide to get ground metres per pixel, multiply to convert into the new projection. Inverting it keeps every test green and moves the map by cos²(lat) — 2.6x at 52°N — which then *also* drags the centre off, because a wrongly-zoomed view gets clamped by its extent. Found by measuring, not by looking.
  - **`fromLonLat`/`toLonLat` from `ol/proj` are hardcoded to EPSG:3857** and were used ~50 times across the OL services; they are replaced by `toMapCoord`/`toLonLatCoord`/`featureProjectionOf`, which read the projection *from the map* rather than from module state, so the inset sub-map built by `MapFactoryService` keeps its own answer. `viewProjectionOf` is deliberately defensive (services get the map before it has a view, and tests pass stubs).
  - **Vector tiles survive the switch.** OL 10 reprojects them in the canvas renderer (`renderer/canvas/VectorTileLayer.js` clones each feature and applies the transform); the long-standing GitHub issues saying otherwise are stale. Verified in a browser: Equal Earth, EPSG:6933 and polar LAEA all render OSM vector tiles with labels. Caveats that are real: the transform is per-vertex with no densification (sparse long segments cut corners), source zoom is picked through a `metersPerUnit` ratio so decluttering is less tidy, and a Mercator-sourced basemap leaves a blank disc at the pole (data stops at ±85°).
  - **A projection must declare the latitudes it may be *measured* over** (`latitudeRange`, default the whole world). Polar stereographic sends its antipode to infinity: sampling EPSG:3031 across the globe gives an extent 4·10²³ m wide, OL derives its resolutions from that, and the map **hangs** laying out a tile grid for a world ten billion times too big — no error, just a frozen tab. `worldExtentOf` samples only inside the range and refuses anything wider than 60 000 km (`MAX_SANE_EXTENT`), so a future bad definition fails loudly instead of freezing. Switching to a regional projection also recentres the view (`centreWithinProjection`): a centre inside the band is left exactly alone, one outside jumps to the *middle* of the band, not the nearest edge — choosing the Antarctic projection from Europe should show Antarctica, not a screen half-filled with the blank past the extent.
  - **A view in degrees hangs the map, so every projection in the catalog is metre-based.** `ol/source/VectorTile.js` scales a source resolution with `resolution / sourceMetersPerUnit / viewMetersPerUnit` — a degree view divides by ~111 319 where it should multiply, so the source is asked for its deepest zoom and then enumerates millions of tiles for one screen. Reproduced with `nl.json` (vector tiles): the tab froze seconds after switching to EPSG:4326; `demo.json` never showed it. EPSG:4326 is therefore not offered at all — `ESRI:54001` (`+proj=eqc`, metres) is the same picture — and `ensureViewProjection` refuses any projection whose units are degrees.
  - **Zoom numbers are projection-relative** — a view's resolutions derive from its projection's extent — so the same `zoom` means a different scale after a switch. `setProjection` preserves *ground scale* and lets the zoom number fall where it may; config/permalink zoom values are only comparable within one projection.
- **Tool registration is one object** (`src/tools/tool-registry.ts`): `TOOL_REGISTRY` declares each tool once — `id`, `tag`, `placement` (`toolbar`/`standalone`/`both`), `label`, `icon`, optional `aliases`/`metadataAliases`/`loaderAliases`, `bundled`, `container`, `offered`. `TOOL_ELEMENT_TAGS`, `STANDALONE_TAGS`, `DEFAULT_TOOL_METADATA`, `KNOWN_TOOLS`, `SUBTOOL_CONTAINER_TYPES`, `BUNDLED_TOOL_IDS` and `canonicalToolId` are all **derived** from it; `dynamic-layout.ts` re-exports them, which is where most callers still import them from. The one thing not derived is the `import()` thunk per tool in `bootstrap/tool-loader.ts`, because only a literal specifier is statically analysable by the bundler — `tests/tool-registration.test.ts` fails if the two disagree, if `bundled` disagrees with what `webmapx-core-bundle.ts` imports, or if a `tag` names a component file that does not exist. Renaming a tool means adding an `aliases` entry, never a second row per map: configs in the wild use the old spelling, and duplicated rows are how a spelling ends up registered in three lists and forgotten in the fourth.
  - **Validation ships as its own entry point.** `src/config-lib.ts` (`@edugis-org/webmapx/config`, built to `dist-lib/webmapx-config.js`) exports `validateConfig`, the tool registry and `CONFIG_SCHEMA_VERSION` with **no DOM and no CSS** — `src/lib.ts` is the app and pulls in Lit, Shoelace and every component, which a config check cannot load in a bare Node process. `src/cli/validate-config.ts` is the same validator behind `webmapx-validate` (`npm run validate:config` locally), exiting non-zero on errors and, with `--strict`, on warnings; this is what lets a config repository's CI gate on the *same* code the browser runs at a pinned package version, instead of a second implementation that drifts. Running the CLI over real configs is also how two validator bugs surfaced that unit tests had not: `layerData.attributeMetadata` was rejected as an unknown key, and a composite layer's sublayers were checked only against top-level sources — 122 false errors on `nl.json`, since a `type: 'style'` layer's own `sources` map is exactly what makes it self-contained.
  - **`CONFIG_SCHEMA_VERSION` is 0, deliberately** (`src/config/schema-version.ts`): pre-1.0, nothing about the config format is promised, and configs are still all ours — a tool may be renamed as long as our configs are renamed with it. The number exists now because a version can be bumped and never unbumped, so starting at the floor keeps every number above it free and leaves **1** to mean the schema release 1 actually supports. The `"version": 1` older configs carried was a meaningless literal and has been rewritten to 0. A config declaring a *newer* version warns and still loads; missing or older says nothing, since there is nothing below 0 to migrate from yet. Migrations belong with release 1.
  - **The config validator knows the tool names too** (`validateToolName`/`validateToolItems` in `config/validator.ts`), because both places a config names a tool drop an unknown one in silence — a typo and a tool from a newer webmapx look identical otherwise. A **top-level `tools` section is accepted for any known tool, not just a standalone one**: a section is also where a toolbar tool's parameters live (`tools.search` holds the provider while the button comes from a toolbar's `items`), and getting that rule wrong warns on every shipped config at once. Always warnings, never errors — a config naming a tool this build lacks must still produce a working map.

- **Tool panel width override**: `webmapx-tool-panel.ts` defaults to a fixed 300px width but any tool can widen it — statically via a `panel-width` attribute on the tool element, or dynamically by dispatching a bubbling `webmapx-panel-width` event (`detail: { toolId, width }`, ignored unless `toolId` matches the currently active tool). The stories tool uses the dynamic form to apply `StoryConfig.width` per story and reset to default on close.
- **Sub-tool containers (`toolbox` / `menu`, `SUBTOOL_CONTAINER_TYPES` in `dynamic-layout.ts`)**: both hold other tools inside one panel — `webmapx-toolbox-tool` as a scrolling icon row, `webmapx-menu-tool` as a drill-in list with submenus (back button, breadcrumb, cross-level search from 8 entries, ARIA menu keyboard nav: roving tabindex + arrows/Home/End/←/→; Escape is left to `webmapx-tool-panel`, whose document-capture listener would win anyway). Config nests them via `items` to any depth, but the DOM they build is always **flat**: `appendSubTools` makes every sub-tool a direct child of the container and encodes nesting as a `menu-path` attribute plus a `groups` JSON attribute (submenu label/icon), because a nested element would be out of reach of the container's single content slot. A toolbox flattens nested containers outright (no submenu UI). `webmapx-modal-tool` skips `ToolManager` registration for anything inside either container (`closest('webmapx-toolbox-tool, webmapx-menu-tool')`) — the container owns sub-tool exclusivity, and a globally-registered modal sub-tool gets deactivated behind its back. Containers hide inactive children with `[hidden]` + `inert` only, never a forced `display`, so each sub-tool keeps its own `:host` display (draw is `flex`). `testpages/setup.html` edits the top level of each container (`CONTAINER_TOOL_IDS`; override keys namespaced by container type); deeper submenus are preserved on save but hand-edited in JSON.
- Layer ordering: handled in generic layer code, not per-engine. Drag-reorder in the legend (`webmapx-layer-overview.ts`) calls `adapter.moveLayer(layerId, beforeLayerId)`, which reorders `store.mapLayers` (key order = bottom-to-top stack, legend shows it reversed) and delegates to each engine's `MapLayerService.moveLayer`.
  - **Cesium limitation (inherent, not fixable):** imagery layers are baked into the globe surface texture; vector primitives/entities always render above all imagery. Vector-vs-raster reorder has no effect — only within-type reorder (`reapplyImageryOrder` for imagery) works.
  - **Leaflet (pane-per-layer):** each logical layer gets its own `map.createPane()` (`webmapx-<id>`, created in `MapLayerService.ensurePane`, passed via `pane` option through `LeafletLayerFactory` and the Allmaps `WarpedMapLayer`). `reapplyLogicalOrder` sets pane z-index = 300 + position in `logicalOrder`, so cross-type (raster vs vector) reorder works. Base 300 keeps catalog layers above `tilePane` (200) and below `overlayPane` (400), where runtime/tool layers (draw, measure, highlights) live in default panes and always render on top; those inline layers are still reordered by remove/re-add within their pane. Panes are removed on `removeLayer` (no Leaflet API — deletes from `map._panes`).
  - **`logicalOrder` vs `mapLayers` divergence (cesium/leaflet):** both engines track imagery/vector layer order in their own `logicalOrder` array, separate from the generic `store.mapLayers`. Layers whose source type isn't handled by that engine's `MapLayerService.addLayer` (e.g. `vector` source type in leaflet/cesium) fall back to `core.addLayer` and are never added to `logicalOrder`. `moveLayer`'s `beforeLayerId` can reference such an untracked layer — both services resolve this by walking `mapLayers` order forward to the nearest layer that IS in `logicalOrder`, instead of falling back to "push to top".
- **Legend empty-label convention:** For `match`/`case` expressions, the fallback (default) value is always pushed with label `''`. The legend skips any case where `label === ''`. To hide a case from the legend — including the fallback — give it an empty string label. To show it, give it an explicit label like `'other'`, `'unknown'`, `'overige'`, etc. This matches the EduGIS convention.
- **Attribute metadata (`metadata.attributes`):** Controls display of feature properties in the info tool and legend labels for `match`/`case` expressions. Defined as `{ translations: [{ name, translation, unit, valuemap?, ... }] }`.
  - **`valuemap`** — array of `{ value, label, operator? }` entries. Used by both the info tool (translates raw feature property values) and the legend (translates `match` keys and `case` condition thresholds into display labels). For `case` expressions, `operator` (`'=='`, `'<'`, `'<='`, etc.) disambiguates between conditions on the same threshold value, enabling range labels like `"0 - 20 inh/km²"` instead of `"< 20 inh/km²"`.
  - **String reference** — `metadata.attributes` can be a string key instead of an inline object, e.g. `"attributes": "pop_dens"`. The legend resolves it from `layerData.attributeMetadata[key]` (stored in `state.attributeMetadata`). Use this to share one definition across many layers that use the same property names, avoiding repetition in config. Define the catalog in `layerData.attributeMetadata` in the config JSON.
- **Theming — two independent token axes** (`src/theme/webmapx-style-core.css`): `[data-theme="light"|"dark"]` carries **colour only**; `[data-style="atlas"|"folio"|"console"]` carries **form only** (radius, surface alpha/blur/border, shadow, density, label treatment). A style block must not set a colour and a theme block must not set a size — that is what makes every style work in both themes without a combinatorial explosion. `compact`/`glossy` remain as deprecated aliases of `console`/`atlas`. Components consume tokens with a literal fallback so they render standalone; `--color-surface-rgb` exists so a style can compose its own alpha. Floating chrome (panels, rail, control clusters) is kept consistent by the `--webmapx-surface-*` and `--webmapx-hit-size` tokens themselves, not by a shared CSS fragment: each component writes the recipe with its own override token layered on top (`--webmapx-panel-bg`, `--webmapx-navigation-border`, `--webmapx-toolbar-button-size`, attribution's `alpha * 0.85`), so no two call sites are identical and a shared fragment matched none of them. `control-surface-styles.ts` is a different thing and is real — it styles Shoelace controls inside shadow roots and has ten importers.
  - **Chrome colour vs map-geometry colour are different systems.** `--color-primary` is muted so it sits quietly in panels; geometry drawn *on* the map (draw vertices, measure lines, routing, markers, inset bbox) needs saturation to survive satellite imagery and must not invert in dark mode. Those canonical values live in `src/theme/data-colors.ts` as TS constants, because engine paint specs are JS and cannot read a CSS variable; `--webmapx-data-*` in the CSS mirrors them so legend dots match what the tool draws. Change one, change the other.
  - **Accessibility is load-bearing here**, not a finishing pass: token values are chosen to meet WCAG AA on their intended ground (the former `#007bff` accent was 3.98:1 and failed for text), `--webmapx-focus-*` is the single focus-ring definition, and the stylesheet ships `prefers-reduced-motion` and `forced-colors` blocks — the latter matters because `atlas`'s translucency is unreadable in Windows High Contrast. Never strip a UA focus outline without putting an equivalent back.
- **Catalog/legend layer rows** derive a swatch from the layer's own paint spec via `deriveLayerSwatch` (`src/utils/layer-swatch.ts`) — no rendering, no network, no extra config. webmapx catalog entries are usually `type: 'style'` containers, so derivation descends into the nested `layers` array and summarises by the most representative sublayer (fill > circle > line > symbol). Expression colours are read **by position**, never by filtering, because `match`/`case` keys are arbitrary author strings that would otherwise be mistaken for CSS named colours. `splitLayerTitle` demotes a trailing technical qualifier (`"OpenStreetMap (xyz)"`) to a muted second line, and both panels use it so a layer is named identically in each.
  - **A swatch belongs to the layer, not to a panel.** `metadata.swatch` on the layer definition holds either a `data:` URL or a plain colour; `deriveLayerSwatch` prefers it over anything it could compute, and every panel that lists layers reads the same value. Only self-contained values are honoured (a remote URL or `javascript:` is ignored) because the value goes straight into a style attribute.
  - **Layers with no derivable paint** (raster basemaps, remote vector styles, Allmaps overlays) get their swatch **baked offline** by `npm run generate:swatches` (`scripts/generate-layer-swatches.ts`, `--help` for options; dry-run unless `--write`). It fetches one representative tile, downscales it in Chromium and stores it as a `data:` URL. **The stored image is 8px square** (`--size`), not swatch-sized: every byte ships in the config to every visitor, and a swatch is a colour with a hint of structure — the browser smooths the upscale for free. 24px tripled the cost for texture nobody can see, and let basemap lettering survive as glyph-shaped noise. **Encoding is whichever of png/webp comes out smaller, which at this size is always png**: a webp file carries ~740 bytes of container before any pixels, so an 8px webp costs four times an 8px png. **A near-uniform tile is not stored as an image at all** — below `FLAT_SPREAD` (per-channel sd of the tile, printed per layer on every run) the mean colour is written instead, seven bytes against ~400. The threshold is measured, not guessed: over demo.json only elevation, cadastral parcels and shaded relief read differently as an image at 18px. This matters at catalog scale — base64 does not compress, so a few hundred pale WMS overlays would otherwise dominate both the config and its gzip. Resolving this at runtime instead would make opening a layer list fire requests at third-party tile hosts for layers the user never added: a privacy leak and a tile-usage-policy problem. `scripts/lib/layer-preview.ts` is **build-time only** and must never be imported by `src/`.
    - Sampling point is Frankfurt/z6 (`PREVIEW_ANCHOR`), but a layer whose `bounds` exclude the anchor is sampled at its own centre, and one with a high `minzoom` at that minzoom — otherwise NL-only or zoom-16+ layers bake a blank tile. `fitZoomToBounds` then zooms in until a tile fits *inside* the extent (two levels past the covering zoom, since a tile merely smaller than the extent can still straddle an edge), because a world-zoom tile over a regional layer is mostly the blank surround. From `URBAN_ZOOM` (13) on, sampling moves to the nearest city in `URBAN_ANCHORS` that the extent contains — at street zoom the centre of a country is a field, and parcels/building footprints only read as something over a town.
    - **Bounds say where a layer *may* have data, not where it does**, so the generator scores each fetched tile by ink coverage (fraction of pixels neither transparent nor near-white, measured on the full-resolution crop) and walks outward through `previewTileCandidates` — then, if every tile is still blank, escalates the zoom (`ZOOM_ESCALATION`). That is what distinguishes an empty tile from a genuinely pale layer. The boost is applied *after* the minzoom floor: PDOK's cadastral map declares minzoom 15.5 but serves nothing until 17, and a pre-floor boost would be swallowed. Sources are addressed by tile index (`{z}/{x}/{y}`), by `{bbox-epsg-3857}`, or via a built WMS `GetMap` (`resolveWmsPreviewUrl`, note WMS 1.3.0 renames SRS→CRS). **A WMS source spells itself two ways**: a bare endpoint with `layers` as a sibling key, or — far more common in real configs — the GetMap query already baked into the `url` (`...?layers=top1000raster`, or a full `REQUEST=GetMap&LAYERS=...`). The resolver reads existing query parameters, keeps them, and overrides only what addresses the tile; handling just the first shape left 59 of nl.json's 193 layers unbaked. A remote style document nests the same two ways too — `layers` at the top (plain maplibre style) or under `source` (webmapx/EduGIS layer document).
    - **Kind is not the test for "needs baking", a derived colour is.** A symbol layer reports kind `unknown` but derives a real colour from `text-color`, and a large catalog is full of label layers; `selectSwatchTargets` skips anything whose background is not `NEUTRAL_SWATCH`, so those cost nothing. Remote `type: 'style'` layers read the style's `background` layer paint, falling back to its most representative sublayer. Allmaps layers read `target.source.id` from the georeference annotation and ask that IIIF service for a thumbnail — read it **structurally**, since pattern-matching ids for "iiif"/"images" matches the AnnotationPage's own URL.
    - **The baker resolves references the same way the app does.** A layer's style `url` may be relative (`styles/openmaptiles/osmbright.json`) — the app resolves it against the config's location (`resolveConfigRelativeUrl` in `config/loader.ts`), and offline it is looked up on disk by walking up from the config file, because configs and styles are usually siblings under a served root rather than in one directory. A source url may carry `{key-…}`, which is substituted from `config/apikeys.json` (the fixed location `src/config/apikeys.ts` fetches) — into the **working copy only**, never into the text written back, so a key cannot leak into a committed config. Skipping either step does not error: the layer just silently ends up without a swatch.
    - `scripts/lib/config-swatches.ts` edits the config as **text**, not via parse/stringify: a JSON round-trip of demo.json rewrites unrelated inline coordinate arrays and buries the real change. Run `npm run generate:swatches` again after adding a raster/style/allmaps layer.
  - **Source shape gotcha:** raw config sources carry `tiles`; the source objects handed to components at runtime carry `url`, which is a **string or an array** (one entry per subdomain). `resolveRasterPreviewUrl` handles all three — missing the array case silently drops every multi-subdomain basemap.
- **TypeScript is the language for tools too.** `scripts/run-ts.mjs` bundles a `.ts` entry point with esbuild and runs it, so CLI tools live in TypeScript alongside the app. The bundle is written under `node_modules/.cache` rather than `os.tmpdir()`, because dependencies stay external and Node resolves them relative to the output file.
- Background switching: `background-group-policy` controls single/exclusive groups
- **`runtimeMap.maxBounds`** `[west, south, east, north]` (lon/lat, MapLibre LngLatBoundsLike flat form) restricts pan/zoom-out to a bbox; "cover" semantics — view stays inside bbox, so with mismatched aspect ratios the full bbox is never visible at once. Antimeridian-crossing boxes rejected by validator. Engine mapping: maplibre `maxBounds` (native), openlayers `View.extent` in 3857 (native), leaflet `maxBounds` + `maxBoundsViscosity: 1` + derived min-zoom re-applied on container resize (`applyMaxBoundsZoomFloor`), cesium soft clamp on `camera.changed` (`enforceMaxBounds` + zoom floor in `clampZoom`/`applyZoomDistanceLimits`).
- Layer config: JSON close to mapbox/maplibre spec (`config/layers.json`, `config/world.json`)
- Allmaps overlay layers integrate with all three 2D engines
- Generic/engine boundary: `BaseAdapter` owns all `store.mapLayers` bookkeeping; engine services are pure engine code and MUST NOT call `registerMapLayer`/`unregisterMapLayer`
  - **Store mirroring lives in `BaseAdapter`, never in callers or engines.** `setLayerVisibility`/`setLayerOpacity`/`setTerrainEnabled`/`setProjection` do the engine work *and* mirror the result into the store (`mapLayers[id].visible` / `.transparency`, `terrainEnabled`, `mapProjection`). Callers must not dispatch those fields themselves — that duplicate-writer pattern is what previously let engine and store drift apart. `setTerrainEnabled`/`setProjection` delegate the engine half to `protected engineSetTerrainEnabled`/`engineSetProjection` (default: returns false = unsupported) and only dispatch when the engine reports the change applied.
  - **`store.mapProjection`** (`MapProjectionState | null | undefined`) is the tri-state mirror: `undefined` = not known yet (map still loading), `null` = active engine has no runtime projection support, object = current projection. `BaseAdapter` seeds it once from `getProjection()` on the first `mapLoaded`, then re-dispatches the *engine-reported* value (not the requested one) after every successful `setProjection`, so story steps and other tools propagate to the view-mode tool. `getProjection()` still reads live engine state and is what you use to snapshot (stories) or to recover after a rejected set. `webmapx-view-mode-tool` follows the store and suppresses the echo of its own change while a slider is being dragged.
  - **Adapters implement only what differs.** `BaseAdapter` provides concrete pass-throughs for all camera/core methods (`initialize`, viewport, zoom, bearing, pitch, `fitBounds`, `project`/`unproject`, cursor/pan/dblclick, `getNavigationCapabilities`, `getElevation`), the logical-layer pass-throughs (`getSourceData`, `queryLayerFeatures`, `getLayerSourceLayers`, `removeLogicalLayer`), the `engineAddLayer`/`engineRemoveLayer`/`engineAddSource`/`engineRemoveSource` defaults (executor-first, core fallback), and unsupported-feature defaults (`setProjection` → false, `getProjection`/`isTerrainEnabled` → null, `setTouchCaptureEnabled` → no-op). A concrete adapter supplies `core`/`logicalLayerExecutor`/`markerService` via the three `protected get*()` hooks and overrides a base method only where its engine genuinely deviates (e.g. maplibre's native-source-id retry in `getSourceData`/`getSource`, its composite-sublayer guard in `engineAddLayer`).
  - `store.terrainEnabled` doubles as a *command* channel: `webmapx-map.ts` dispatches `terrainEnabled: true` from config/permalink restore and `webmapx-3d-tool` reacts by calling `adapter.setTerrainEnabled()` against the active hillshade layer. Those two dispatches are deliberate, not redundant mirrors.
