# webmapx

Modular web map UI with adapters for MapLibre, OpenLayers, Leaflet, and Cesium.

## Stack

- **Framework**: Lit (web components), TypeScript, Vite
- **Map engines**: MapLibre GL, OpenLayers (ol), Leaflet, Cesium
- **Overlays**: @allmaps (leaflet, maplibre, openlayers)
- **UI**: Shoelace components
- **State**: `src/store/map-state-store.ts`

## Architecture

```
src/
  map/                    # Engine adapters + services
    IMapInterfaces.ts     # Shared interfaces
    base-adapter.ts       # Abstract base: store, hasLayer, layer bookkeeping
    maplibre-adapter.ts   # MapLibre adapter (extends BaseAdapter)
    openlayers-adapter.ts
    leaflet-adapter.ts
    cesium-adapter.ts
    maplibre-services/    # Engine-specific services (pure engine, no store bookkeeping)
    openlayers-services/
    leaflet-services/
    cesium-services/
    layer-source-utils.ts
    logical-layer-executor.ts
    runtime-layer-utils.ts
    visible-layer-utils.ts
    adapter-registry.ts
  components/             # Lit web components (webmapx-*)
  store/                  # Map state (IMapState.ts, map-state-store.ts, map-events.ts)
  config/                 # Config types
  tools/                  # Map tools
  utils/                  # Shared utilities
  workers/                # Web workers
```

## Key patterns

- **Stories tool** (`webmapx-stories-tool.ts`, config `stories` section, `src/config/types.ts`): a guided-tour tool — `StoryConfig` → `StoryChapterConfig` → `StoryStepConfig`. Each step's `state` is authored as human-readable `StoryStepConfigState` (`layers`, `hiddenLayers`, `view: { center, zoom, bearing?, pitch? }`, `transparency`, `projection`, `terrain`) and converted via `toStoryStepState` (`src/config/story-step-state.ts`) into the short-key `StoryStepState` — the same shape as a decoded permalink (`PermalinkState` in `src/utils/permalink.ts`) — camera + layer visibility/opacity + terrain, with no tool state — so applying a step is a set of direct `adapter.setViewport`/`setBearing`/`setPitch`/`setLayerVisibility`/`setLayerOpacity`/`setProjection`/`setTerrainEnabled` calls. Layer visibility/transparency are additionally mirrored into `store.mapLayers` (same dual update `webmapx-layer-overview.ts` does for its own toggle/slider handlers) so the legend reflects what a story step is showing; camera/projection/terrain are not dispatched, since `captureStartState`/`restoreStartState` already give the story its own restore path for those and no UI needs them live. `captureStartState`/`restoreStartState` snapshot and restore camera + layer visibility/opacity (both engine and store) + projection + terrain around the whole story, so it's still a transient overlay — the map ends up exactly as it was before the story opened, and nothing leaks into the permalink (which is generated from `store` state after the story has closed). Unlike permalink restore (which only toggles layers already loaded and reports the rest as missing), a story step lazily adds any referenced layer that isn't loaded yet via `mapHost.addLayerRequest({ layerId })` — the same catalog-lookup path `webmapx-search-tool.ts`/`webmapx-buffer-tool.ts` use — tracked in `addedLayerIds`. A story-added layer no longer referenced by the current step is removed outright (not just hidden) as soon as you navigate away from it, and any layer still in `addedLayerIds` when the story closes is removed then too — so which layers the legend lists depends only on the current step, never on which steps happened to be visited earlier. A layer that was already on the map before the story opened is never removed by the story (only hidden/restored), since the story doesn't own it. Step content is `html` (inline, sanitized) or `htmlUrl` (fetched, resolved relative to the config file's URL at load time in `config/loader.ts`; relative `src`/`href` inside the fetched HTML are then resolved against that URL too, via `sanitizeAbstractHtml(html, baseUrl)` in `utils/sanitize-html.ts`).
- **Tool panel width override**: `webmapx-tool-panel.ts` defaults to a fixed 300px width but any tool can widen it — statically via a `panel-width` attribute on the tool element, or dynamically by dispatching a bubbling `webmapx-panel-width` event (`detail: { toolId, width }`, ignored unless `toolId` matches the currently active tool). The stories tool uses the dynamic form to apply `StoryConfig.width` per story and reset to default on close.
- **Sub-tool containers (`toolbox` / `menu`, `SUBTOOL_CONTAINER_TYPES` in `dynamic-layout.ts`)**: both hold other tools inside one panel — `webmapx-toolbox-tool` as a scrolling icon row, `webmapx-menu-tool` as a drill-in list with submenus (back button, breadcrumb, cross-level search from 8 entries, ARIA menu keyboard nav: roving tabindex + arrows/Home/End/←/→; Escape is left to `webmapx-tool-panel`, whose document-capture listener would win anyway). Config nests them via `items` to any depth, but the DOM they build is always **flat**: `appendSubTools` makes every sub-tool a direct child of the container and encodes nesting as a `menu-path` attribute plus a `groups` JSON attribute (submenu label/icon), because a nested element would be out of reach of the container's single content slot. A toolbox flattens nested containers outright (no submenu UI). `webmapx-modal-tool` skips `ToolManager` registration for anything inside either container (`closest('webmapx-toolbox-tool, webmapx-menu-tool')`) — the container owns sub-tool exclusivity, and a globally-registered modal sub-tool gets deactivated behind its back. Containers hide inactive children with `[hidden]` + `inert` only, never a forced `display`, so each sub-tool keeps its own `:host` display (draw is `flex`). `testpages/setup.html` edits the top level of each container (`CONTAINER_TOOL_IDS`; override keys namespaced by container type); deeper submenus are preserved on save but hand-edited in JSON.
- Layer ordering: handled in generic layer code, not per-engine. Drag-reorder in the legend (`webmapx-layer-overview.ts`) calls `adapter.moveLayer(layerId, beforeLayerId)`, which reorders `store.mapLayers` (key order = bottom-to-top stack, legend shows it reversed) and delegates to each engine's `MapLayerService.moveLayer`.
  - **Cesium limitation (inherent, not fixable):** imagery layers are baked into the globe surface texture; vector primitives/entities always render above all imagery. Vector-vs-raster reorder has no effect — only within-type reorder (`reapplyImageryOrder` for imagery) works.
  - **Leaflet (pane-per-layer):** each logical layer gets its own `map.createPane()` (`webmapx-<id>`, created in `MapLayerService.ensurePane`, passed via `pane` option through `LeafletLayerFactory` and the Allmaps `WarpedMapLayer`). `reapplyLogicalOrder` sets pane z-index = 300 + position in `logicalOrder`, so cross-type (raster vs vector) reorder works. Base 300 keeps catalog layers above `tilePane` (200) and below `overlayPane` (400), where runtime/tool layers (draw, measure, highlights) live in default panes and always render on top; those inline layers are still reordered by remove/re-add within their pane. Panes are removed on `removeLayer` (no Leaflet API — deletes from `map._panes`).
  - **`logicalOrder` vs `mapLayers` divergence (cesium/leaflet):** both engines track imagery/vector layer order in their own `logicalOrder` array, separate from the generic `store.mapLayers`. Layers whose source type isn't handled by that engine's `MapLayerService.addLayer` (e.g. `vector` source type in leaflet/cesium) fall back to `core.addLayer` and are never added to `logicalOrder`. `moveLayer`'s `beforeLayerId` can reference such an untracked layer — both services resolve this by walking `mapLayers` order forward to the nearest layer that IS in `logicalOrder`, instead of falling back to "push to top".
- **Legend empty-label convention:** For `match`/`case` expressions, the fallback (default) value is always pushed with label `''`. The legend skips any case where `label === ''`. To hide a case from the legend — including the fallback — give it an empty string label. To show it, give it an explicit label like `'other'`, `'unknown'`, `'overige'`, etc. This matches the EduGIS convention.
- **Attribute metadata (`metadata.attributes`):** Controls display of feature properties in the info tool and legend labels for `match`/`case` expressions. Defined as `{ translations: [{ name, translation, unit, valuemap?, ... }] }`.
  - **`valuemap`** — array of `{ value, label, operator? }` entries. Used by both the info tool (translates raw feature property values) and the legend (translates `match` keys and `case` condition thresholds into display labels). For `case` expressions, `operator` (`'=='`, `'<'`, `'<='`, etc.) disambiguates between conditions on the same threshold value, enabling range labels like `"0 - 20 inh/km²"` instead of `"< 20 inh/km²"`.
  - **String reference** — `metadata.attributes` can be a string key instead of an inline object, e.g. `"attributes": "pop_dens"`. The legend resolves it from `layerData.attributeMetadata[key]` (stored in `state.attributeMetadata`). Use this to share one definition across many layers that use the same property names, avoiding repetition in config. Define the catalog in `layerData.attributeMetadata` in the config JSON.
- **Theming — two independent token axes** (`src/theme/webmapx-style-core.css`): `[data-theme="light"|"dark"]` carries **colour only**; `[data-style="atlas"|"folio"|"console"]` carries **form only** (radius, surface alpha/blur/border, shadow, density, label treatment). A style block must not set a colour and a theme block must not set a size — that is what makes every style work in both themes without a combinatorial explosion. `compact`/`glossy` remain as deprecated aliases of `console`/`atlas`. Components consume tokens with a literal fallback so they render standalone; `--color-surface-rgb` exists so a style can compose its own alpha. Floating chrome (panels, rail, control clusters) shares one recipe via `surfaceHostStyles`/`surfaceStyles`/`surfaceButtonStyles` in `components/internal/surface-styles.ts` — the counterpart to the existing `control-surface-styles.ts` for Shoelace controls inside shadow roots.
  - **Chrome colour vs map-geometry colour are different systems.** `--color-primary` is muted so it sits quietly in panels; geometry drawn *on* the map (draw vertices, measure lines, routing, markers, inset bbox) needs saturation to survive satellite imagery and must not invert in dark mode. Those canonical values live in `src/theme/data-colors.ts` as TS constants, because engine paint specs are JS and cannot read a CSS variable; `--webmapx-data-*` in the CSS mirrors them so legend dots match what the tool draws. Change one, change the other.
  - **Accessibility is load-bearing here**, not a finishing pass: token values are chosen to meet WCAG AA on their intended ground (the former `#007bff` accent was 3.98:1 and failed for text), `--webmapx-focus-*` is the single focus-ring definition, and the stylesheet ships `prefers-reduced-motion` and `forced-colors` blocks — the latter matters because `atlas`'s translucency is unreadable in Windows High Contrast. Never strip a UA focus outline without putting an equivalent back.
- **Catalog/legend layer rows** derive a swatch from the layer's own paint spec via `deriveLayerSwatch` (`src/utils/layer-swatch.ts`) — no rendering, no network, no extra config. webmapx catalog entries are usually `type: 'style'` containers, so derivation descends into the nested `layers` array and summarises by the most representative sublayer (fill > circle > line > symbol). Expression colours are read **by position**, never by filtering, because `match`/`case` keys are arbitrary author strings that would otherwise be mistaken for CSS named colours. `splitLayerTitle` demotes a trailing technical qualifier (`"OpenStreetMap (xyz)"`) to a muted second line, and both panels use it so a layer is named identically in each.
  - **A swatch belongs to the layer, not to a panel.** `metadata.swatch` on the layer definition holds either a `data:` URL or a plain colour; `deriveLayerSwatch` prefers it over anything it could compute, and every panel that lists layers reads the same value. Only self-contained values are honoured (a remote URL or `javascript:` is ignored) because the value goes straight into a style attribute.
  - **Layers with no derivable paint** (raster basemaps, remote vector styles, Allmaps overlays) get their swatch **baked offline** by `npm run generate:swatches` (`scripts/generate-layer-swatches.ts`, `--help` for options; dry-run unless `--write`). It fetches one representative tile, downscales it to 24px in Chromium and stores it as a webp `data:` URL — at that size a tile reads as its own average colour. Resolving this at runtime instead would make opening a layer list fire requests at third-party tile hosts for layers the user never added: a privacy leak and a tile-usage-policy problem. `scripts/lib/layer-preview.ts` is **build-time only** and must never be imported by `src/`.
    - Sampling point is Frankfurt/z6 (`PREVIEW_ANCHOR`), but a layer whose `bounds` exclude the anchor is sampled at its own centre, and one with a high `minzoom` at that minzoom — otherwise NL-only or zoom-16+ layers bake a blank tile. Sources are addressed by tile index (`{z}/{x}/{y}`), by `{bbox-epsg-3857}`, or via a built WMS `GetMap` (`resolveWmsPreviewUrl`, note WMS 1.3.0 renames SRS→CRS). Remote `type: 'style'` layers read the style's `background` layer paint, falling back to its most representative sublayer. Allmaps layers read `target.source.id` from the georeference annotation and ask that IIIF service for a thumbnail — read it **structurally**, since pattern-matching ids for "iiif"/"images" matches the AnnotationPage's own URL.
    - `scripts/lib/config-swatches.ts` edits the config as **text**, not via parse/stringify: a JSON round-trip of demo.json rewrites unrelated inline coordinate arrays and buries the real change. Run `npm run generate:swatches` again after adding a raster/style/allmaps layer.
  - **Source shape gotcha:** raw config sources carry `tiles`; the source objects handed to components at runtime carry `url`, which is a **string or an array** (one entry per subdomain). `resolveRasterPreviewUrl` handles all three — missing the array case silently drops every multi-subdomain basemap.
- **TypeScript is the language for tools too.** `scripts/run-ts.mjs` bundles a `.ts` entry point with esbuild and runs it, so CLI tools live in TypeScript alongside the app. The bundle is written under `node_modules/.cache` rather than `os.tmpdir()`, because dependencies stay external and Node resolves them relative to the output file.
- Background switching: `background-group-policy` controls single/exclusive groups
- **`runtimeMap.maxBounds`** `[west, south, east, north]` (lon/lat, MapLibre LngLatBoundsLike flat form) restricts pan/zoom-out to a bbox; "cover" semantics — view stays inside bbox, so with mismatched aspect ratios the full bbox is never visible at once. Antimeridian-crossing boxes rejected by validator. Engine mapping: maplibre `maxBounds` (native), openlayers `View.extent` in 3857 (native), leaflet `maxBounds` + `maxBoundsViscosity: 1` + derived min-zoom re-applied on container resize (`applyMaxBoundsZoomFloor`), cesium soft clamp on `camera.changed` (`enforceMaxBounds` + zoom floor in `clampZoom`/`applyZoomDistanceLimits`).
- Layer config: JSON close to mapbox/maplibre spec (`config/layers.json`, `config/world.json`)
- Allmaps overlay layers integrate with all three 2D engines
- Generic/engine boundary: `BaseAdapter` owns all `store.mapLayers` bookkeeping; engine services are pure engine code and MUST NOT call `registerMapLayer`/`unregisterMapLayer`
  - **Store mirroring lives in `BaseAdapter`, never in callers or engines.** `setLayerVisibility`/`setLayerOpacity`/`setTerrainEnabled`/`setProjection` do the engine work *and* mirror the result into the store (`mapLayers[id].visible` / `.transparency`, `terrainEnabled`, `mapProjection`). Callers must not dispatch those fields themselves — that duplicate-writer pattern is what previously let engine and store drift apart. `setTerrainEnabled`/`setProjection` delegate the engine half to `protected engineSetTerrainEnabled`/`engineSetProjection` (default: returns false = unsupported) and only dispatch when the engine reports the change applied.
  - **`store.mapProjection`** (`MapProjectionState | null | undefined`) is the tri-state mirror: `undefined` = not known yet (map still loading), `null` = active engine has no runtime projection support, object = current projection. `BaseAdapter` seeds it once from `getProjection()` on the first `mapLoaded`, then re-dispatches the *engine-reported* value (not the requested one) after every successful `setProjection`, so story steps and other tools propagate to the view-mode tool. `getProjection()` still reads live engine state and is what you use to snapshot (stories) or to recover after a rejected set. `webmapx-view-mode-tool` follows the store and suppresses the echo of its own change while a slider is being dragged.
  - **Adapters implement only what differs.** `BaseAdapter` provides concrete pass-throughs for all camera/core methods (`initialize`, viewport, zoom, bearing, pitch, `fitBounds`, `project`/`unproject`, cursor/pan/dblclick, `getNavigationCapabilities`, `getElevation`), the logical-layer pass-throughs (`getSourceData`, `queryLayerFeatures`, `getLayerSourceLayers`, `removeLogicalLayer`), the `engineAddLayer`/`engineRemoveLayer`/`engineAddSource`/`engineRemoveSource` defaults (executor-first, core fallback), and unsupported-feature defaults (`setProjection` → false, `getProjection`/`isTerrainEnabled` → null, `setTouchCaptureEnabled` → no-op). A concrete adapter supplies `core`/`logicalLayerExecutor`/`markerService` via the three `protected get*()` hooks and overrides a base method only where its engine genuinely deviates (e.g. maplibre's native-source-id retry in `getSourceData`/`getSource`, its composite-sublayer guard in `engineAddLayer`).
  - `store.terrainEnabled` doubles as a *command* channel: `webmapx-map.ts` dispatches `terrainEnabled: true` from config/permalink restore and `webmapx-3d-tool` reacts by calling `adapter.setTerrainEnabled()` against the active hillshade layer. Those two dispatches are deliberate, not redundant mirrors.
